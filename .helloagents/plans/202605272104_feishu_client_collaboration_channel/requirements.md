# 飞书客户端协作通道需求

## 背景

当前 Orca 已具备飞书机器人 App ID / App Secret 配置、凭证检查、长连接状态展示，以及飞书消息触发本地 orchestration run 的基础能力。但用户在桌面客户端里看不到飞书发来的消息，也不能从 Orca 给飞书回复。

这会造成产品体验断层：设置页显示事件通道连接成功，但用户无法确认飞书消息是否进入 Orca、无法查看原始消息、无法手动回复，也无法把飞书聊天与本地 run 状态关联起来。

本方案目标是把飞书集成从“后台事件入口”补完整为“桌面端可见、可回复、可转任务、可追踪”的协作通道。

## 目标

- 在 Orca 客户端增加飞书协作通道入口，能看到飞书机器人收到的消息。
- 飞书消息在客户端内形成会话列表和消息流，展示来源、发送人、时间、处理状态和关联 run。
- 用户能在 Orca 客户端直接回复飞书聊天。
- 用户能把某条飞书消息转为 Orca 任务，或让默认规则自动创建任务。
- Orca run 的关键状态能回写到对应飞书会话，并在客户端里同步显示。
- 连接状态、最近事件、最近发送失败、权限/配置错误有明确诊断。
- 保持“每个用户配置自己的飞书机器人 App”的私有层设计，不把 App Secret 或消息内容写入团队公共配置。

## 范围

- 新增本地飞书消息存储与查询 API。
- 新增飞书事件入库：`im.message.receive_v1` 收到后先保存消息，再交给编排适配器处理。
- 新增飞书回复 API：从客户端输入文本，通过飞书 IM OpenAPI 回发到原 chat。
- 新增飞书消息订阅：renderer 能实时收到 incoming/outgoing/status 更新。
- 新增客户端 UI：
  - 飞书通道入口。
  - 会话列表。
  - 消息流。
  - 回复输入框。
  - “转为任务 / 查看 run / 停止 run / 查看诊断”操作。
- 新增 run 关联：`chatId/messageId/runId/taskId/gateId` 可查询。
- 复用现有飞书机器人编排逻辑：
  - `状态/status`
  - `停止/stop`
  - `帮助/help`
  - `继续 <内容>`
  - 默认创建任务
- 复用现有 run status publisher，但将发送结果写回本地消息流。
- 全部用户可见文案纳入 i18n，中英文都要覆盖，中文要自然准确。

## 非范围

- 不做完整 IM 客户端，不支持群管理、成员管理、历史消息全量拉取、富文本编辑、图片/文件收发。
- 不支持多个 active run 并行；仍沿用当前 Orca 单 active run 约束。
- 不让 Orca 自动创建飞书应用、申请权限、发布版本、拉机器人入群。
- 不把飞书作为项目知识唯一事实源；项目知识仍以 repo 内 `.helloagents/` 为准。
- 不实现复杂自然语言意图分类；需要时后续再引入明确的 intent 层。
- 不默认持久化敏感 token；tenant token 仍只放内存缓存。

## 用户故事

- 作为普通用户，我在设置页填入 App ID 和 App Secret 后，能看到“凭证有效”和“事件通道已连接”是两个不同状态。
- 作为普通用户，我在飞书里给机器人发消息后，能在 Orca 客户端飞书通道里看到这条消息。
- 作为普通用户，我能在 Orca 客户端给这条飞书消息所在会话回复文本。
- 作为普通用户，我能点击“转为任务”，让 Orca 用该消息创建本地任务。
- 作为普通用户，我能在飞书和 Orca 客户端两边看到任务已创建、进行中、等待确认、失败、完成等状态。
- 作为普通用户，当回复失败或消息没有事件到达时，我能看到具体原因，而不是只看到“连接成功”。

## 成功标准

- 长连接成功后，飞书发来的文本消息能实时出现在 Orca 客户端消息流。
- Orca 客户端可以向原飞书 chat 发送文本回复，并在消息流中显示发送中、已发送、发送失败。
- 飞书消息能手动或自动创建 `source=feishu` 的 orchestration run。
- run 状态回推到飞书后，本地消息流也能显示对应 outgoing/status 消息。
- active run 冲突时，飞书和客户端都显示清晰提示，不重复创建第二个 run。
- pending decision gate 出现时，飞书和客户端都能看到等待确认状态；用户在飞书回复或客户端操作后都能 resolve。
- 去重有效：同一飞书 message_id 重放不会重复显示为多条未处理消息，也不会重复创建 run。
- 断线重连后状态准确：客户端能看到最后连接时间、最后事件时间、最后错误。
- 新增逻辑有测试覆盖：
  - 消息存储与去重。
  - 收到飞书消息入库。
  - 客户端回复发送与失败状态。
  - 消息转任务。
  - run 状态回写本地消息流。
  - i18n 文案完整性。
- 验证命令通过：
  - `corepack pnpm run typecheck:node`
  - `corepack pnpm run typecheck:web`
  - `corepack pnpm run check:i18n-copy`
  - 相关 vitest

## 关键约束

- 飞书事件 handler 需要快速完成：入库、去重、排队后返回；编排启动和回发异步执行。
- 飞书同一个 App 多客户端长连接时事件会分发到其中一个客户端；设置页和文档要继续提示“每人使用自己的机器人 App”。
- 回发内容必须脱敏，不能把本机绝对路径、App Secret、token、keychain 错误细节原样发到飞书。
- 本地消息存储需要控制容量，避免长期运行无限增长。
- SSH 场景不能假设所有 run 都发生在本机路径；消息 UI 只展示抽象 run/task 状态。
