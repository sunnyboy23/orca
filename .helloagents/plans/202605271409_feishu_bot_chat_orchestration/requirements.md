# 飞书机器人聊天编排入口需求

## 背景

当前 Orca 的飞书设置只验证 `App ID` 和 `App Secret` 能否换取飞书访问凭证。用户期望的是完整机器人入口：在飞书聊天里向机器人发送任务，Orca 桌面端接收消息、执行本地编排，并把任务进度、等待确认和结果回发到飞书会话。

项目中已经存在飞书 webhook/gateway、消息解析、卡片构造、decision gate 解析和 `orchestration.run({ source: "feishu" })` 的基础能力，但缺少桌面端长连接事件客户端、IM 发送能力、飞书消息到本地编排的适配器，以及运行状态回推链路。

## 范围

- 使用飞书开放平台长连接模式接收机器人消息，桌面端无需公网回调 URL。
- 用户只需要在 Orca 中填写自己的 `App ID` 和 `App Secret`；飞书后台的机器人权限、事件订阅、长连接模式启用和应用发布由用户自行完成。
- Orca 设置页提供真实的飞书机器人连接状态、连接/断开控制、错误原因和最近事件时间。
- 收到飞书文本消息后，Orca 将消息转换为本地 `orchestration.run`，来源标记为 `feishu`，并保存 chat/message 关联。
- 飞书聊天中能够看到当前执行的任务状态、关键进度、等待确认、失败和完成结果。
- 用户能通过飞书聊天继续指令，至少支持：
  - 发起新任务。
  - 查询当前任务状态。
  - 停止当前任务。
  - 对 pending decision gate 回复选项或点击卡片按钮。
- 回发到飞书的文本和卡片必须脱敏，不泄露本机绝对路径、token、App Secret、keychain 引用等敏感信息。
- 保持桌面端、CLI 和现有 orchestration UI 能力不回归。

## 非范围

- 不实现多个 active run 并行；沿用 Orca 当前同一时间一个 active run 的约束。
- 不让 Orca 代用户在飞书后台创建应用、开权限、发布版本或邀请机器人进群。
- 不把个人 `App Secret`、飞书 access token、chat 绑定写入团队公共配置或代码仓库。
- 不在本阶段实现复杂自然语言意图分类；先用明确文本规则和默认“创建任务”行为。
- 不把飞书作为项目知识事实源；项目知识仍以 repo 内 `.helloagents/` 为准，飞书知识库作为共享入口。

## 成功标准

- 设置页能显示 `未配置`、`凭证有效`、`事件通道连接中`、`事件通道已连接`、`事件通道失败` 等真实状态。
- 在飞书中给机器人发送普通文本后，Orca 能创建一条 `source=feishu` 的 run，并立即回发“已收到/已创建 run”消息。
- 编排 run 任务状态变化时，飞书聊天能收到节流后的状态更新。
- 出现 decision gate 时，飞书聊天能收到可操作卡片或明确选项；用户回复或点击后能 resolve gate。
- 用户发送“状态/停止/帮助”等指令时，Orca 能做对应操作并回发结果。
- 所有新增飞书消息处理、命令解析、状态回推和设置状态逻辑有单元测试或 mocked 集成测试。
- `corepack pnpm run typecheck:node`、`corepack pnpm run typecheck:web`、相关 vitest 通过。

## 关键约束

- 飞书长连接事件处理需要快速返回；收到事件后只做去重、入队和确认，实际启动 run 与发送回执异步执行。
- 飞书同一应用如果多个客户端同时长连接，事件会被分发到其中一个客户端；产品上需要提示每个用户使用自己的机器人应用，避免团队成员共享同一个 App 导致消息被随机消费。
- Orca 需要处理重复事件、重复消息和客户端重连，不能因为飞书重推而重复创建 run。
- 当 Orca 已有 active run 时，飞书新任务默认回发“已有任务执行中”，并提示用户先停止或等待完成。
